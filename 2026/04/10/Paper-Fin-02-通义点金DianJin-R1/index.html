Paper-Fin-02_通义点金DianJin-R1

💡DianJin-R1 论文核心总结
DianJin-R1 是阿里云通义点金团队推出的金融领域推理增强大模型框架，基于通义千问 2.5 基座研发，通过结构化监督微调与强化学习，大幅提升大模型在金融场景的推理、数值计算与合规审核能力。

一、核心背景
金融领域大模型推理面临三大难点：专业知识要求高、数值计算需精准、合规规则需严格遵守，通用推理模型在金融场景效果不佳，因此需要专项优化。

二、核心数据：DianJin-R1-Data
构建高质量金融推理数据集，融合三类数据源并经严格筛选与校验：

  1. CFLUE：中文金融考试题库，过滤后保留 2.6 万 + 高质量推理题；
  2. FinQA：英文金融数值推理数据集，筛选 4800 + 样本；
  3. CCC：自研中文金融客服合规审核数据集，1800 条真实对话样本。数据处理采用GPT-4o 校验、多智能体生成推理步骤，确保推理逻辑与答案精准。

三、模型训练：两阶段优化

  1. 监督微调（SFT）基于 Qwen2.5-7B/32B-Instruct，训练模型用输出推理链输出最终结果，学习结构化金融推理逻辑。
  2. 强化学习（RL）采用GRPO 算法，设置双重奖励：
  • 格式奖励：约束输出符合 + 结构；
  • 准确率奖励：引导模型输出正确答案。

四、实验效果
在 5 大基准测试中，DianJin-R1 表现突出：

  1. 金融任务：DianJin-R1-32B 在 CFLUE（86.74%）、FinQA（80.82%）、CCC（96.00%）均登顶，远超基座模型与通用推理模型；
  2. 通用推理：MATH-500、GPQA-Diamond 成绩较基座模型显著提升；
  3. 成本优势：CCC 任务中，单模型单次调用（1 次 API）即可达到多智能体系统（8.15 次 API）的效果，算力成本大幅降低。

五、核心结论与未来方向

  1. 核心价值：结构化监督 + 强化学习能有效增强金融推理，单模型可替代高成本多智能体系统；
  2. 未来计划：优化强化学习策略、加入工具增强推理（计算器、检索引擎），进一步提升金融场景精度与稳健性。

简介

大型语言模型（LLMs）在金融领域的有效推理仍然是一个核心挑战，因为金融任务通常需要领域特定知识、精确的数值计算以及严格遵守合规规则。我们提出了DianJin-R1，一种增强推理的框架，通过推理增量的监督和强化学习来解决这些挑战。我们的方法的核心是DianJin-R1-Data，一个由CFLUE、FinQA和一个专有合规语料库（Chinese Compliance Check，CCC）构建的高质量数据集，结合了多样化的金融推理场景和经过验证的注释。我们的模型，DianJin-R1-7B和DianJin-R1-32B，从Qwen2.5-7B-Instruct和Qwen2.5-32B-Instruct微调而来，使用生成推理步骤和最终答案的结构化格式。为了进一步完善推理质量，我们应用组相对策略优化（GRPO），一种强化学习方法，结合了双重奖励信号：一个促进结构化输出，另一个奖励答案正确性。我们在五个基准测试中评估我们的模型：三个金融数据集（CFLUE、FinQA和CCC）和两个通用推理基准（MATH-500和GPQA-Diamond）。实验结果表明，DianJin-R1模型在复杂金融任务中始终优于其非推理模型。此外，在真实世界的CCC数据集上，我们的单次调用推理模型相比那些需要显著更多计算成本的多代理系统表现相当甚至更好。这些发现证明了DianJin-R1在通过结构化监督和奖励对齐学习加强金融推理方面的有效性，为现实世界应用提供了一个可扩展且实用的解决方案。

一、金融推理的痛点与本文解法

在金融场景中应用通用推理大模型面临极其严苛的挑战：

  1. 领域知识壁垒与计算精度要求：金融任务不仅需要深厚的垂直领域知识，还对精准的数值计算能力有极高要求。
  2. 严格的合规性限制：模型输出必须严格遵守金融监管与合规规则，容错率极低。
  3. 复杂结构的解析困难：需要专门的推理策略来同时处理结构化的金融信息和开放式的应用问题。
    本文破局思路 (DianJin-R1 Framework)：
    提出基于    推理增强监督 (Reasoning-augmented Supervision)     与 强化学习 (Reinforcement Learning, GRPO) 相结合的训练框架。核心贡献在于构建了高质量数据集 DianJin-R1-Data，并通过双重奖励机制实现了金融逻辑与合规要求的对齐。

二、DianJin-R1-Data 数据集构造

与通用推理数据直接蒸馏不同，DianJin-R1 针对三种截然不同的金融场景（客观题、数值问答、合规对话）设计了差异化的数据合成与过滤 Pipeline。

数据源与硬核过滤机制

共采用三个核心数据源，并通过严格的前置过滤保证数据难度：

  • **CFLUE (开源中文金融基准)**：包含 38,638 道金融资格模拟考试选择题。
    • 长度过滤：剔除少于 15 个 token 的题目，拒绝低信息量样本。
    • 难度过滤：剔除 LLaMA-3.1-8B 和 Qwen2.5-7B-Instruct 都能直接答对的题目，倒逼模型进行深层推理。
    • 歧义过滤：利用 GPT-4o 剔除表述模棱两可的问题，确保题目有唯一确定解。
  • **FinQA (开源英文数值推理)**：包含 8,281 个基于财报的问答对，复用上述的长度与难度过滤机制。
  • **CCC (私有中文合规审查数据集)**：来自真实金融客服对话的质检系统。通过人工复核，确保违规与合规样本分布均衡。

多路径推理轨迹生成 (Reasoning Generation)

  • 对于CFLUE数据集，我们首先使用gpt-4o把多项选择题转换为开放式问题，接着利用deepseek-r1获取推理数据。
  • 对于FinQA数据集，其本身是开放式问题，我们无须进行额外转换。其余处理步骤同CFLUE保持一致。
  • 对于CCC数据集，我们获取Multi-Agent System工作流中所有的推理步骤并使用gpt-4o合并为一个最终的推理过程和推理结果。

路径 A：CFLUE (多选题 $\rightarrow$ 开放式推理)

  1. 题型转化：首先使用 GPT-4o 将多选题转化为不带选项的开放式问题，并提取标准精确答案。
  2. 蒸馏生成：使用 DeepSeek-R1 生成包含内部思考过程的 CoT ($r_i$) 和预测答案 ($a_i$)。
  3. **GPT-4o 双重校验 (Verifier)**：不仅校验预测答案 $a_i$ 是否匹配金标准 $y_i$，还深度校验生成的 CoT ($r_i$) 与官方解析 ($e_i$) 的逻辑一致性。
  4. 重试与兜底：最多允许 3 次重试 ($T=3$)。若彻底失败，则将其标记为“困难非推理样本” ($G_{CFLUE}$)，留作后续 RL 阶段使用。

路径 B：FinQA (英文数值问答)

  • 直接沿用路径 A 的开放式问题生成、DeepSeek-R1 蒸馏以及 GPT-4o 校验的 Pipeline。

路径 C：CCC (金融合规复杂图谱 $\rightarrow$ Multi-Agent 合成)
合规判断无法通过单次对话直接得出，需依赖复杂的业务规则图谱。

  1. 节点级 Agent 分解：将合规判断工作流拆解，为每个条件节点分配一个单独的 LLM Agent (基于 Qwen2.5-72B-Instruct)。
  2. 中间态组装：各节点 Agent 依次输出中间层思维链 $(r^0_i, …, r^n_i)$ 与中间答案。
  3. GPT-4o 融合提炼：若最终节点的结论与金标准一致，则调用 GPT-4o 将所有碎片化的中间 CoT 融合为一段连贯、统一的最终思维链 $r_i$。

三、模型训练（两阶段训练）

训练过程分为两步，底座模型选用 Qwen2.5-7B-Instruct 和 Qwen2.5-32B-Instruct。

Figure 2: Illustration of two-step training for DianJin-R1.

阶段1：通过SFT学习推理

  • 训练数据：混合了高质量推理数据集 $R_{CFLUE}$, $R_{FinQA}$, $R_{CCC}$。
  • 格式强制对齐：输入问题 $x$，目标输出被严格规范为 推理过程最终答案 的结构化格式。
  • 硬件与参数：使用 NVIDIA A100 GPUs，DeepSpeed Zero-3 优化。Learning Rate 设定为 $1.0 \times 10^{-5}$，Sequence Length 16K，使用 bf16 精度训练 3 个 Epochs。采用 16 steps 的梯度累积模拟大 Batch Size。

阶段2：利用RL增强推理（GRPO Training）

为了进一步榨取模型在困难样本上的推理潜力，采用 GRPO (Group Relative Policy Optimization) 算法。

  • 训练数据：使用第一阶段沉淀下来的困难非推理样本 $G_{CFLUE_{MCQ}}$。
  • 超参数设计：每条样本生成 8 个 rollouts，Train Batch Size 为 1024，Rollout Batch Size 为 256。Learning Rate 降低至 $1.0 \times 10^{-6}$，采样 Temperature 设为 0.6，训练 5 个 Epochs。
  • **双重领域奖励机制 (Reward Shaping)**：
    1. **Format Reward (格式奖励)**：输出必须包含且仅包含一对确切的 … 和 … 标签，且标签外无冗余文本。符合得 1 分，否则得 0 分。
    2. **Accuracy Reward (准确率奖励)**： 标签内包裹的内容必须与参考答案绝对精确匹配，匹配得 1 分，否则得 0 分。

四、核心实验与评估结果

论文在 3 个金融基准 (CFLUE, FinQA, CCC) 和 2 个通用基准 (MATH-500, GPQA-Diamond) 上进行了测试。对于存在表述差异的 FinQA 和 CCC，使用 GPT-4o 作为裁判 (Judge) 进行评估。

  1. 核心性能跃升
  • 超越通用推理模型：DianJin-R1-32B 在金融任务上取得了惊艳的成绩，CFLUE 达到 86.74，FinQA 达到 80.82，CCC 达到 96.00。在这些垂直任务上，其表现甚至超越了以推理著称的 DeepSeek-R1 (其在FinQA上反而存在掉点现象)。
  • 小模型的大潜力：DianJin-R1-7B (CCC准确率 94.50) 全面碾压其 Base 模型 Qwen2.5-7B-Instruct (CCC准确率 55.00)。
  1. 深度消融实验结论
  • RL 阶段的数据偏置问题：SFT 提升了所有基准的成绩，而叠加 RL 后，除英文 FinQA 外的所有基准成绩均有进一步提升。论文推测，由于 RL 训练仅使用了中文的 CFLUE 困难样本，导致其对英文 FinQA 产生了一定的领域/语种偏置。

    Q：在当前的 DianJin-R1 模型（经过 RL 训练后）上，将 CFLUE-MCQ 的中文问题翻译成英文再提问，其效果会变差吗？
    A：当前 DianJin-R1 模型的 RL 训练策略确实可能导致其在处理非训练语言（如英文）的任务时性能下降，即使任务内容本身是它熟悉的。

    • 原始中文 CFLUE-MCQ：模型在 RL 后对此类问题的处理能力是最强的，因为 RL 就是专门用这类数据进行优化的。
    • 翻译后的英文 CFLUE-MCQ：虽然问题内容与原始中文 CFLUE-MCQ 相同，但语言变成了英文。对于这个经过纯中文 RL 训练的模型来说，它现在面对的是一个“陌生”的英文输入。模型在 SFT 阶段学到的英文处理能力很可能已经被 RL 阶段的中文优化所削弱。因此，它的表现很可能不如直接用中文提问时好，甚至可能比仅经过 SFT（未 RL）的版本还要差。

  • 数据集规模的统治力：单独使用 CFLUE (超3.1万条数据) 进行 SFT 时，带来的提升最为显著，将总体平均准确率从 59.26 直接拉升至 65.67。同时混合三大数据集能达到全局最优。
  1. 【金融落地亮点】业务系统降本增效

在复杂的 CCC 合规检测任务中：

  • 传统基线：直接使用单节点 Qwen2.5-72B 准确率仅 55.50。
  • 多智能体堆叠：采用 Multi-Agent 架构虽然能将 72B 模型的准确率拉满到 95.00，但代价极其高昂，单条样本平均需要消耗 8.15 次 API Call。
  • DianJin-R1 降维打击：DianJin-R1-32B 仅需 **1 次 API Call (Single-call)**，便能达到 96.00 的准确率，在性能持平甚至反超的前提下，实现了推理成本的指数级降低。

五、结论与未来演进方向

DianJin-R1 证明了结合高质量结构化监督与对齐奖励强化学习，能够实质性提升 LLM 解决复杂、高容错率金融问题的能力。
Future Work 明确规划：

  1. Fine-grained Reward Shaping：探索更细粒度的奖励机制与分层策略学习 (Hierarchical policy learning) 以进一步打磨推理质量。
  • 包括：通过在 RL 阶段加入英文样本来解决上述 RL 阶段的数据（语种）偏置问题。
  1. **Tool-Augmented Reasoning (工具增强)**：计划赋予金融模型动态调用外部计算器、检索系统和规则引擎的能力，解决高风险金融应用中极端数值计算的稳健性（robustness）问题。

⭐️DianJin-R1 论文核心创新深度拆解与行业落地启示

一、核心创新模块一：数据工程 ——SFT 范式的颠覆性突破

1.1 核心范式：Multi-Agent 合规数据合成（Multi-Agent 生成 → 单体蒸馏）

1.1.1 适用场景
该范式专门适配需要模型懂规则、能过质检、会审文档的多规则、强流程、高合规要求的复杂业务决策场景（如合规风控、研报审核），而非通用金融问答场景。
在金融合规（CCC 数据集）场景中，DianJin-R1 摒弃了让单个大模型 “一口吃成胖子” 的做法，设计了一套精密的流水线式数据生产逻辑，这也是 Fin-R1 所没有的业务逻辑建模。

1.1.2 四步流水线式实现逻辑

  1. 节点级拆解（专家化）：真实金融质检包含几十条细分规则（如是否提示风险、是否核实客户身份），DianJin-R1 为每一个逻辑判断节点设立一个专属 Agent（由 Qwen2.5-72B-Instruct 扮演）。
  • 核心优势：单 Agent 仅需专注判断单一规则，极大降低了长文本下的 “金融幻觉” 和规则遗漏率。
  1. 中间态组装（碎片化推理）：每个 Agent 独立输出自己的判断和极简的中间推理过程（$r^0_i, r^1_i…$），此时的数据是碎片化的，无法直接用于训练 R1 这类需要端到端长思维链的模型。
  2. 前置校验（答案一致性校验）：这是数据生产流程的核心准入环节。Multi-Agent 生成的中间推理，必须先经过「最终答案与金标准 100% 匹配」的校验，只有匹配成功的样本才会进入后续 GPT-4o 缝合环节，失败样本会被重试（最多 3 次）或直接丢弃，从源头保证了训练数据的答案准确性。
  3. GPT-4o 缝合师（全局平滑）：这是范式的核心关键步骤。利用 GPT-4o 作为 “缝合师”，在已知最终正确答案（金标准）的前提下，把碎片化的中间推理组合成逻辑连贯、符合 … 格式的全局思维链，完成从 Multi-Agent 系统到单体 R1 模型的知识蒸馏闭环。

1.1.3 核心落地启示
复杂业务的推理数据是 “编排” 出来的，不是 “生成” 出来的。用 Agent 组团针对不同规则进行并发式、多维度的 “初审与打点”，保证规则覆盖率；再用强模型（GPT-4o）在 中将这些碎片化的专家意见做端到端的长链条逻辑总结，保证文本连贯性。这种 “规则分治 + 强模型缝合” 的蒸馏数据构建法，是获取极高质量 SFT 数据的标准范式。

1.2 与 Fin-R1 数据范式的本质代差

  • Fin-R1 的数据逻辑是「通用蒸馏→质量过滤」，解决的是金融领域有没有高质量 CoT 的问题，核心是把通用推理能力迁移到全金融场景；
  • DianJin-R1 的 Multi-Agent 编排范式，解决的是通用蒸馏根本做不出来的、复杂业务流程的 CoT 数据问题 —— 合规场景的推理需要严格遵循监管规则的分步判断，单模型蒸馏的 CoT 极易出现规则遗漏、逻辑跳步，而分治 + 缝合的方式从根源上保证了推理链的规则覆盖率和逻辑严谨性，这是两者数据范式的核心代差。

1.3 范式的工程价值闭环

该范式的核心巧思是：把高成本的多 Agent 调用留在了训练侧，而非推理侧。Multi-Agent 系统只在数据生产阶段使用，一旦完成知识蒸馏，落地时仅需调用单体 7B/32B 模型，完美平衡了「训练数据的高质量」和「推理落地的低成本」，与后续 ROI 落地法则形成完整的逻辑呼应。

1.4 范式的适用前提与边界

该方法的核心前提是业务流程可拆解为独立、无交叉的规则节点；若业务规则之间存在强耦合、无法原子化拆解，该范式则不适用。

二、核心创新模块二：GRPO 的踩坑与克制化设计

Fin-R1 和 DianJin-R1 均采用了 GRPO 算法，但两者的底层设计逻辑存在本质区别：DianJin-R1 的 GRPO 是反通用范式的—— 通用 R1、Fin-R1 用 GRPO 做全量能力强化，而 DianJin-R1 用 GRPO 仅做针对性的能力补全，RL 不负责教模型 “怎么推理”，只负责解决 SFT 没学会的 “硬骨头”。

2.1 核心工程风险：数据偏置导致的能力退化

这是 DianJin-R1 论文中暴露的、极具行业参考价值的工程细节，值得所有垂域大模型研发高度警惕。

2.1.1 现象与根因分析

  • 现象：DianJin-R1 经过 SFT 后，英文数值推理（FinQA）成绩大幅提升；但叠加 GRPO 后，FinQA 成绩反而下降（从 80.28 掉到 77.72）。
  • 根因分析：DianJin-R1 在 RL 阶段，仅使用了中文 CFLUE-MCQ 的困难样本，无英文 / 数值推理类数据，直接导致语种与场景分布偏置。GRPO 是一种极度敏感的对齐算法，单一语种和特定题型的 Reward 信号，会让模型对中文多选题产生 “过拟合”，从而污染原本在 SFT 阶段建立的英文和数值推理能力。

2.1.2 研发避坑原则
在做垂域 RL 时，如果 Reward 数据集分布不均衡，极易引发 “灾难性遗忘”。RL 强化的是特定分布下的推理轨迹，必须保证 RL 数据池的多样性。

2.2 极简高效的双重 Reward 设计逻辑

DianJin-R1 的 Reward 设计非常克制，仅包含 格式奖励（Format）和结果精准度（Accuracy） 两项，没有使用复杂的长度惩罚或人工偏好模型（RM）。这充分证明：在金融这种 “对错黑白分明” 的强规则场景下，基于规则的 Rule-based Reward 是最高效的设计。

2.3 垂域 RL 落地的实操避坑方案

基于 DianJin-R1 的踩坑经验，可总结出行业通用的落地避坑方案：

  1. 分布对齐原则：RL 数据池必须和 SFT 数据池保持语种、题型、场景的分布一致性，避免单一分布过拟合；
  2. 多任务 Reward 加权：即使只强化核心业务场景，也要在 Reward 中加入基础数值计算、跨场景推理的辅助奖励，避免灾难性遗忘；
  3. 轻对齐原则：垂域场景下 RL 极易偏科，需采用小学习率、少轮次的 “轻对齐”，而非高强度优化（DianJin-R1 仅训练 5 个 epoch）。

三、核心创新模块三：ROI 与金融场景落地法则

3.1 告别 “堆叠调用” 的成本黑洞

3.1.1 核心 ROI 论证
DianJin-R1 给出了金融大模型落地最清晰的 ROI（投资回报率）论证：用 72B 模型叠加 Agent 跑合规任务，准确率 95%，但单次任务需要消耗 8.15 次 API 调用，在真实的高并发金融场景中，成本是毁灭性的。
而通过将这条 Multi-Agent 轨迹蒸馏进 DianJin-R1-32B，模型实现了Single-call（单次调用）达到 96% 的准确率。DianJin-R1 提出的 “1 次 API 调用 vs 8 次 API 调用” 的降本效益，正是金融机构最核心的落地诉求。

3.1.2 高并发场景下的全维度价值
金融机构的合规质检、研报审核等场景，均为日均百万级的高并发调用，8 次 API 调用与 1 次 API 调用的差距，不仅是 8 倍的资金成本差，更关键的是推理延迟、系统稳定性、合规可追溯性的质的差异：

  • 多 Agent 系统的推理过程分散在多轮调用中，无法形成完整、可审计的推理链，难以满足金融监管的可追溯要求；
  • 单体模型的 标签包含完整的推理过程，单次调用即可完成全流程判断，同时满足了低成本、低延迟、强合规三大核心落地要求。

这也印证了大模型的核心演进方向：将云端的复杂系统 “压缩” 进端侧或本地化部署的单体模型中。

3.2 金融大模型研发的 ROI 优先级排序

行业通用结论：金融大模型的收益贡献占比，数据质量＞SFT 工程＞RL 算法＞模型参数量。
DianJin-R1 的消融实验明确验证：仅靠高质量 SFT 数据（如单加 3.1 万条 CFLUE SFT 数据），就能让底座模型的表现产生质的飞跃（准确率拉升超 6 个百分点），贡献了全流程 80% 以上的效果收益，而 RL 的增量收益不足 20%。
这也充分说明：在金融领域，扎实的 SFT 脏活累活（去歧义、校验解析、过滤低智样本）带来的收益，远大于盲目调优 RL 算法参数。

四、总结：金融推理大模型的 4 条生存法则

  1. 放弃 “参数内卷” 和 “算法万能论”：垂直金融领域，不要指望通用算法或大参数量让模型自发涌现行业专家能力。金融大模型的核心差异化，从来不是 GRPO 等算法框架本身，而是「Reward 函数的金融场景化定义」和「CoT 数据的业务逻辑厚度」。
  2. “数据蒸馏” 决定模型下限，“业务逻辑编排” 决定模型上限：仅复刻通用大模型的标准化蒸馏流程，只能保证模型达到行业及格线；DianJin-R1 告诉我们，当单模型蒸馏无法覆盖复杂业务规则时，要用「多 Agent 规则分治 + 强模型逻辑缝合」的工程化手段，逆向编排、合成具备深度业务逻辑的专家级 CoT 数据，这才是金融大模型拉开代差的核心。
  3. 警惕垂域 RL 的 “盲目对齐” 与 “灾难性遗忘”：DianJin-R1 的踩坑经验明确验证（在中文困难样本上做 GRPO 导致英文 FinQA 成绩下滑），垂域场景下的 GRPO 是极易偏科的敏感算法。金融落地中，若 Reward 设计和训练数据仅聚焦单一业务场景，极易导致模型丧失基础的数值计算、跨场景通用推理能力，必须保证 RL 阶段的数据分布与 SFT 全局对齐。
  4. 推理成本是金融大模型落地的生死铁律：技术方案再惊艳，若需要多轮 API 调用（如需要调用 8 次 API 才能完成一次质检）、大参数量模型才能完成单次业务推理，在金融机构的高并发、强合规场景中就无法规模化落地。DianJin-R1 将 Multi-Agent 专家系统的复杂链式推理，蒸馏压缩进 7B/32B 单体模型的单次推理 标签中，实现「成本指数级下降、效果持平反超、合规性全面满足」，才是金融大模型从 POC 走向规模化落地的核心路径。
